## 1️⃣ PRÉSENTATION DU PROJET

### Objectif métier

QHSE Air Bot est une application d’assistance destinée aux responsables QHSE (Qualité, Hygiène, Sécurité, Environnement).  
L’application permet :

- de poser des questions réglementaires (Code du travail, guides INRS, base ARIA) et d’obtenir des réponses sourcées,  
- de consulter des indicateurs de qualité de l’air issus de l’API WAQI en temps réel,  
- de centraliser des conversations et des notes liées au suivi QHSE.

L’objectif métier est de **sécuriser les décisions QHSE** en donnant accès rapidement à une information fiable, contextualisée et expliquée par une IA spécialisée.

### Type de modèle et problème adressé

Le projet s’appuie sur une architecture **RAG (Retrieval-Augmented Generation)** hybride, qui combine :

- un **moteur de recherche sémantique** (base vectorielle) pour retrouver les passages pertinents dans les documents QHSE,  
- une **injection de données temps réel** (SQL) pour les métriques environnementales (Qualité de l'air),
- un **modèle de langage** (LLM – DeepSeek / OpenAI) pour générer une réponse rédigée.

Type de modèle :

- **NLP / LLM** (modèle de langage génératif) utilisé en mode “chatbot expert”,
- couplé à des embeddings et à une base vectorielle pour la phase de retrieval.

Problème adressé :

- difficulté pour les responsables QHSE à trouver rapidement l’information réglementaire ou environnementale,
- besoin d’un assistant conversationnel capable de **citer les sources** et d’intégrer des données en temps réel (ex: pollution à Lille aujourd'hui).

### Contraintes techniques

- manipuler des données hétérogènes (textes réglementaires statiques vs mesures WAQI dynamiques),  
- gérer la **latence** de l’IA et garantir une réponse même si le LLM principal est indisponible (fallback),  
- respecter les contraintes **RGPD** (données utilisateurs, logs),  
- assurer une intégration fluide dans l'écosystème existant (PostgreSQL, Docker).

### Environnement technique

- **Langage :** Python 3.11  
- **Backend API :** FastAPI  
- **Frontend :** Streamlit  
- **Base de données :** PostgreSQL  
- **IA / RAG :** FAISS, DeepSeek/OpenAI, LangChain  
- **Monitoring :** Prometheus, Loguru, Evidently  
- **CI/CD :** GitHub Actions

## 2️⃣ C9 – DÉVELOPPEMENT D’UNE API REST EXPOSANT LE MODÈLE

### A. Architecture technique

L’API REST (FastAPI) expose le modèle RAG via des endpoints sécurisés.

Architecture globale :

- **FastAPI** sert de passerelle unique.
- Le module `src/rag/pipeline/rag_chain.py` orchestre la logique IA :
  - Il interroge la base vectorielle pour le contexte documentaire.
  - Il interroge la base SQL (`MesureWAQI`) pour le contexte temps réel (ex: AQI).
  - Il assemble le prompt et appelle le LLM.

### B. Endpoints développés

- **`POST /rag/chat`** : Endpoint principal du chatbot.
  - Entrée : `{ "question": "Quelle est la qualité de l'air à Lille ?" }`
  - Traitement : 
    1. Analyse de l'intention (Réglementaire vs Temps réel).
    2. Récupération du contexte hybride (Vecteurs + SQL).
    3. Génération de la réponse.
  - Sortie : `{ "answer": "À Lille, l'indice AQI est de 45 (Bon)...", "sources": [...] }`

- **`GET /waqi/`** : Accès direct aux données brutes de qualité de l'air.
- **`/health` & `/metrics`** : Endpoints de supervision.

### C. Sécurisation

- **Authentification JWT** : Tous les endpoints sensibles nécessitent un header `Authorization: Bearer <token>`.
- **Validation Pydantic** : Les payloads sont strictement typés pour éviter les injections.
- **Gestion des erreurs** : Les erreurs du LLM ou de la base de données sont capturées et renvoient des codes HTTP 503 ou 422 appropriés, sans exposer la stack trace.

### D. Versionnement

- Code hébergé sur GitHub (`mila1515/qhse-air-bot`).
- Branches : `main` (prod), `dev` (intégration), `mlops` (features).
- Documentation OpenAPI générée automatiquement sur `/docs`.

## 3️⃣ C10 – INTÉGRATION API IA DANS UNE APPLICATION

### A. Application existante

Le frontend est une application **Streamlit** modulaire.

### B. Intégration API

L’intégration se fait via le service `src/frontend/services/chat_client.py`.

- **Appels HTTP** : Utilisation de `requests` pour appeler l’API FastAPI.
- **Gestion de session** : Le token JWT est stocké en `st.session_state` et injecté dans chaque requête.
- **Expérience Utilisateur** :
  - Affichage progressif de la réponse (streaming simulé ou bloc complet).
  - Gestion des cas d'erreur (ex: API indisponible) avec des messages conviviaux.
  - Le chat supporte le contexte (historique conversationnel).

### C. Tests d’intégration

- **Tests de bout en bout** : Scénarios validant qu'une question posée sur le frontend reçoit bien une réponse générée par le backend RAG.
- **Validation des flux** : Vérification que les données temps réel (WAQI) remontent bien dans l'interface de chat.

## 4️⃣ C11 – MONITORAGE DU MODÈLE IA

### A. Métriques choisies

- **Performance RAG** :
  - `rag_query_latency_seconds` : Temps de réponse moyen du RAG.
  - `rag_fallback_activation_total` : Nombre de bascules vers le LLM de secours (OpenAI -> Local/DeepSeek).
  - `db_connection_status` : Disponibilité de la base PostgreSQL (1=UP, 0=DOWN).
- **Qualité des données** :
  - `etl_last_run_success_timestamp` : Fraîcheur des données WAQI (Timestamp Unix).
  - `air_quality_index_value` : Dernière valeur AQI collectée par ville.

### B. Outils et Implémentation

- **Prometheus** :
  - Collecte les métriques exposées sur l'endpoint `/metrics` de l'API.
  - Intervalle de scraping configuré à 5s dans `prometheus.yml`.

- **Grafana (Visualisation)** :
  - **Provisioning Automatique** : Configuration "Zero-Touch" via Docker volumes.
    - `datasources.yml` : Connexion automatique à Prometheus.
    - `dashboards.yml` : Chargement automatique du tableau de bord "QHSE Monitoring".
  - **Dashboard QHSE** : Visualisation temps réel de la latence RAG, des erreurs et de la qualité de l'air.

- **Evidently AI (Data Drift & Quality)** :
  - **Rapports (Reports)** : Génération automatique de rapports HTML (Drift & Quality) à chaque exécution du pipeline ETL.
  - **Dashboard Projet** : Interface centralisée pour suivre l'évolution de la qualité des données (WAQI / ARIA) dans le temps.
  - **Architecture** : Service Docker dédié (`evidently`) recevant les snapshots des scripts Python via l'API interne.

- **Automatisation & Orchestration** :
  - **Scheduler Dédié** : Service Docker (`src/scheduler.py`) exécutant automatiquement les tâches de fond.
    - 10:00 : Pipeline ETL (Collecte & Load).
    - 11:00 : Ingestion RAG (Mise à jour connaissances).
  - **Pushgateway** : Agrégation des métriques des tâches batch (ETL) pour exposition vers Prometheus.

### C. Architecture monitoring

Les métriques sont calculées à deux niveaux :
1.  **Service Continu (API)** : Middleware FastAPI exposant `/metrics` en temps réel.
2.  **Tâches Batch (ETL/RAG)** : Le Scheduler déclenche les scripts qui poussent leurs métriques (succès, volume, qualité) vers le **Pushgateway** en fin d'exécution.

### D. Tests environnement bac à sable

Simulation d'incidents :
- Coupure de la base de données -> Vérification de l'alerte `db_connection_status`.
- Latence élevée du LLM -> Vérification de l'impact sur `rag_query_latency_seconds`.

## 5️⃣ C12 – TESTS AUTOMATISÉS DU MODÈLE

### A. Stratégie de test

- **Tests Unitaires** : Validation des fonctions de nettoyage et de formatage des prompts.
- **Tests d'Intégration** : Vérification de la chaîne complète (DB -> RAG -> API).
- **Tests de Robustesse** : Comportement face à des questions hors sujet ou mal formées.

### B. Framework utilisé

- **Pytest** pour l'exécution des tests.
- **Unittest.mock** pour simuler les réponses du LLM (éviter les coûts API pendant les tests).

### C. Couverture

Les tests couvrent les cas nominaux (réponse standard) et les cas d'erreur (fallback, timeout).

### D. Documentation

Procédure d'exécution incluse dans le `README.md` et le workflow CI/CD.

## 6️⃣ C13 – CHAÎNE DE LIVRAISON CONTINUE (MLOPS)

### A. Outils CI/CD

- **GitHub Actions** pour l'orchestration.

### B. Pipeline configuré

Le fichier `.github/workflows/main.yml` définit :
1. **Lint & Security** : `flake8`, `bandit`, `trivy` pour la qualité du code.
2. **Unit Tests** : Exécution de la suite `pytest`.
3. **Build** : Construction de l'image Docker de l'API.
4. **Staging** : Déploiement éphémère via Docker Compose pour valider le démarrage des services (`/health`).
5. **Simulation Prod** : Tagging et release sur la branche `main`.

### C. Fichiers configuration

- Variables d'environnement (`.env`) gérées via les Secrets GitHub.
- Configuration Docker (`docker-compose.yml`) pour reproduire l'environnement iso-prod.

### D. Tests pipeline

Le pipeline bloque le merge si une étape échoue (ex: faille de sécurité critique ou test unitaire rouge), garantissant la qualité du livrable.
